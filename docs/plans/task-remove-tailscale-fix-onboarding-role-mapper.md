# Implementation Proposal: Remove Tailscale from the staging deploy pipeline; fix the broken onboarding role mapper
Status: APPROVED
ADR: none yet (see §10 Q1)    Date: 2026-10-17    Backlog ID: none yet (not filed as an issue)

## 1. Goal

Two independent fixes to `lis-staging`'s deploy pipeline and realm config, bundled into one proposal because both touch `.github/workflows/deploy-staging.yml` and both were found live during the same debugging session:

1. **Remove Tailscale from the deploy pipeline entirely.** The user has disabled their own use of Tailscale and wants the pipeline to stop depending on it — for CI's own SSH access to the droplet, for discovering the app's public-facing hostname, and for TLS termination (`tailscale serve`). Replace all three with the already-live, already-working public-domain path (`https://lis-staging.duckdns.org`, fronted by the `siamas` app's Caddy container, `infra/docker-compose.lis-public.yml` + `infra/nginx-public.conf`) and with plain SSH key auth (already proven working this session, and already how every actual deploy action authenticates — Tailscale currently only provides the *network path*, not the credential).

2. **Fix `infra/keycloak/lis-realm.json`'s broken "roles" client scope.** Its `protocolMappers` array defines only `oidc-usermodel-realm-role-mapper` (populates `realm_access.roles`) — it is missing `oidc-usermodel-client-role-mapper` (populates `resource_access.<client>.roles`). Confirmed live on staging: a `client_credentials` token for `lis-onboarding`, even after its service account was correctly granted the `manage-users`/`view-realm` roles on `realm-management`, carried `"scope": "tenant openid"` and no `resource_access` claim at all, and every Keycloak Admin API call it made 403'd. This almost certainly means `POST /onboarding/signup` (ADR-0040, FEAT-049) has never actually worked against this realm config on any environment where `defaultClientScopes` plus `fullScopeAllowed: true` were assumed sufficient on their own.

## 2. Affected files

## 5. Assumptions & autonomous decisions

- **CI's own SSH access needs no new secret or mechanism** — `secrets.DEPLOY_SSH_KEY` already authenticates every `ssh`/`scp` call in both workflows today; Tailscale currently only supplies the *network path* to reach `secrets.DEPLOY_HOST` (implying that secret currently holds the droplet's Tailscale IP/hostname, not its public one). Removing the two Tailscale steps and repointing `DEPLOY_HOST` to the droplet's real public IP (`157.230.10.221`, already confirmed reachable via plain SSH throughout this session) is sufficient — no workflow code change needed for the SSH mechanism itself, only the secret's *value* (a manual step for the repo owner, not something this proposal's code changes can do — see §10).
- **The public domain becomes a new GitHub Actions repo variable, not a hardcoded string.** Proposing `vars.STAGING_PUBLIC_DOMAIN` (e.g. `lis-staging.duckdns.org`, no scheme) rather than hardcoding `https://lis-staging.duckdns.org` directly into the workflow — matches the existing convention of `secrets.DEPLOY_HOST` being externally configurable rather than baked into the file, and means a future domain change (or a second environment) doesn't need a workflow edit.
- **Keycloak is still reached under the same domain/port as the app (443), not a separate `:8443`** — per `infra/nginx-public.conf`'s own routing (`/realms/` and `/resources/` proxy to `keycloak:8080` on the same public listener `web` uses). The smoke test's current two-URL check (`https://${MAGIC_DNS_NAME}/` then `https://${MAGIC_DNS_NAME}:8443/realms/lis/...`) becomes one domain with two paths, no port distinction.
- **The public overlay gets copied and reapplied automatically on every deploy**, not left as a manual post-deploy step — directly addresses what broke repeatedly this session (every manual `docker compose ... --force-recreate` without the overlay silently dropped public access until manually reapplied). Proposing this as part of the existing "Copy compose file and realm config to droplet" + "Pull and restart on droplet" steps: `scp` the two overlay files alongside the existing ones, and change every `docker compose ... up -d`/`rm -f -s`/`restart` invocation in the remote script to pass both `-f docker-compose.yml -f docker-compose.lis-public.yml` instead of just the base file.
- **The role-grant fix is a new idempotent post-boot step, not a change to what `del(.users)` strips.** Simpler and more robust than trying to relocate the service-account role mapping to a part of the realm JSON the strip step won't touch (Keycloak's realm-export format always nests service-account role mappings under `users`, by convention — fighting that convention seems more fragile than just re-granting the role every deploy, the same way the client-secret regenerate-and-sync block already does for a different reason). Proposing it run right after the existing Keycloak-health-check retry loop, before `docker compose up -d api web` (api's first real request, from a live user hitting `/onboarding/signup`, could otherwise race a deploy that hasn't granted the role yet).
- **`rollback-staging.yml` gets the identical fix**, not left on the old Tailscale-dependent path — it would otherwise silently diverge and break the next time it's actually used (same class of gap `docker-pnpm-monorepo-deploy` entry #25 describes for env-var wiring across multiple surfaces).
- **Not in scope:** removing `tailscaled` from the droplet itself (only removing the *pipeline's dependency* on it — the daemon can stay installed, unused, or be removed separately by the user outside this change); any change to `apps/web`/`apps/api` source; adding a DigitalOcean Cloud Firewall (a real security hardening step, but a separate decision — see §10 Q3).

## 6. Risks

- **SSH to the droplet is currently unrestricted at the network level** (confirmed via memory: no DigitalOcean Cloud Firewall attached, only SSH port 22 and whatever Caddy fronts on 80/443 are exposed). Tailscale's CI-access role, per `docker-pnpm-monorepo-deploy` entry #3, was originally adopted specifically to *avoid* needing to open plain SSH to GitHub Actions' runner IP ranges at all. Switching CI to plain SSH over the public internet doesn't change the droplet's current actual exposure (it's already open to everyone, not just GitHub) — but it does mean that if a Cloud Firewall is added later, GitHub's own IP ranges would need allowlisting, which entry #3 documents as hitting DigitalOcean's 1,000-source cap. Flagged as a real, open tradeoff, not silently assumed away — see §10 Q3.
- **`tailscale serve`'s automatic Let's Encrypt-equivalent cert issuance/renewal goes away**, replaced by reliance on `siamas-caddy-1`'s own existing cert management for `lis-staging.duckdns.org` (already real, already working, already renewing itself for `siamas`'s own domains) — low risk since this isn't new infrastructure, just an additional domain on an already-functioning cert-renewal setup, but it's a dependency on `siamas`'s own container staying healthy, outside this repo's control.
- **The `extra_hosts` IP mapping in `docker-compose.lis-public.yml` (`lis-staging.duckdns.org:172.18.0.8`, `siamas-caddy-1`'s current internal IP) is not guaranteed stable** — its own header comment already documents this: "any time `siamas-caddy-1` itself is recreated... re-run [`docker network connect`] if this ever starts failing." Automating the overlay's reapply doesn't fix this pre-existing fragility; a future `siamas`-side change could still silently break `lis-staging`'s public access the same way, just without this session's manual debugging path to notice it mid-session. Worth a follow-up health check in the smoke test (confirm the overlay's `extra_hosts` IP still matches Caddy's live IP) — proposed as a nice-to-have, not blocking (§10 Q4).
- **Removing `del(.users)`'s collateral role-strip side effect entirely (an alternative to the new post-boot step) was considered and rejected** — see §5's reasoning. The accepted approach (re-grant every deploy) means a deploy that fails *between* Keycloak becoming healthy and this new step running would leave onboarding broken until the next deploy — same class of partial-deploy risk every other step in this job already carries, not a new risk class.

## 7. Acceptance criteria

- A real `git push` to `main` (or `workflow_dispatch`) triggers `deploy-staging.yml` with zero references to `tailscale`, `TS_OAUTH_CLIENT_ID`/`TS_OAUTH_SECRET`, or `MAGIC_DNS_NAME` anywhere in the job.
- Post-deploy, `https://lis-staging.duckdns.org/` returns 200 and `https://lis-staging.duckdns.org/realms/lis/.well-known/openid-configuration` returns 200 with `issuer` matching the public domain exactly — checked by the workflow's own smoke test, not just manually after the fact.
- A real `POST /onboarding/signup` against the freshly-deployed instance succeeds end-to-end (201, not 403/500) without any manual post-deploy kcadm step — proving both the mapper fix and the new automated role-grant step work together, not just individually.
- `rollback-staging.yml` run (`workflow_dispatch`) also succeeds with the same Tailscale-free smoke test.
- No change in behavior for any currently-passing part of the pipeline (image build/push, Postgres/Valkey/MinIO, catalog seeding, backup/restore scripts) — this proposal's diff should be scoped to exactly the Tailscale/hostname/role-grant logic, confirmed by reviewing the diff before merge.

## 8. Testing plan

- Dry-run the realm JSON mapper fix locally first (`pnpm dev` / local Keycloak container) — confirm a local `client_credentials` token for `lis-onboarding` now carries `resource_access.realm-management.roles` including `manage-users`, before touching staging again.
- `workflow_dispatch` `deploy-staging.yml` manually (not waiting for a real `main` push) to iterate safely — same approach `docker-pnpm-monorepo-deploy` entry #15-21's saga used, each attempt checked via direct `docker compose logs`/`docker exec` evidence, not assumed from a green step alone.
- After a green deploy run, manually re-run this session's own seed script (`POST /onboarding/signup` + two `POST /v1/users` calls) against the fresh deploy to prove the whole chain works without any of the manual kcadm steps this session needed.
- Confirm `rollback-staging.yml` separately, since it's not exercised by a normal `main` push.

## 9. Rollback plan

Each half reverts independently and cheaply:
- **Tailscale removal**: revert the workflow-file diff (`git revert`); re-add `TS_OAUTH_CLIENT_ID`/`TS_OAUTH_SECRET` secrets if they were deleted from repo settings (propose leaving them in place, unused, rather than deleting — cheaper to revert). `DEPLOY_HOST` secret would need to be pointed back at the Tailscale hostname manually.
- **Realm mapper fix**: revert `infra/keycloak/lis-realm.json`'s diff; since Keycloak is fully rebuilt from this file every deploy (`docker compose rm -f -s keycloak`, already true before this proposal), a revert takes effect on the very next deploy with no manual droplet intervention needed.
- **Role-grant step**: simply remove the new step; harmless to leave a previously-granted role in place if reverted (not cleaned up automatically, but not a security regression either — `manage-users`/`view-realm` is the documented minimum-needed grant, same as today).
