## Notes / gotchas for the next session

- **"Code merged" and "acceptance criterion proven" are different facts — now also true at the CI/deploy level, not just the issue-closure level.** This session's central finding: PR Checks/Constitution Gate being green on TASK-029/030's PRs did **not** mean the software was actually deployable — a separate pipeline (Deploy to Staging) was red across both merges for three independent reasons, silently, until this session's orientation caught it. Don't treat "PR Checks passed" as "safe to merge and move on" when a second, independent CI workflow exists for the same change — check it too.
- **A Dockerfile and a CI workflow's own build steps are two separate places that both need updating when a workspace package gets a real first consumer.** `pr.yml` got the `pnpm --filter @lis/db build` fix (TASK-030); `apps/api/Dockerfile` didn't, because nobody thought to check the second build path. Same root cause, two files, one fix applied. If a workspace package gets a *new* consumer again, check both.
- **Local Docker validation before pushing to CI is worth doing for infra fixes** — this session validated the `dist/main.js` + `pnpm deploy` fix with a real local `docker build` + `docker run` before opening PR #180, catching that an earlier attempted fix (`rootDir` alone) produced a *compile error*, not silence, until `vitest.config.ts` was also excluded. Cheaper than a full CI + deploy round-trip per iteration.
- **`pnpm deploy`'s file-inclusion defaults to git/npm-ignore-style rules when a package has no `"files"` field** — and `dist/` is gitignored at this repo's root. Any workspace package that starts using `pnpm deploy --prod` for the first time needs an explicit `"files"` field, or its build output silently never ships. Confirmed against pnpm's own docs (`pnpm.io/cli/deploy`), not guessed.
- **`nest build`'s output path is only `dist/main.js` if `tsconfig.build.json` has an explicit (or correctly-inferred) `rootDir` of `src/`.** Adding any `.ts` config file (e.g. `vitest.config.ts`) directly in the package root — outside `src/` — silently shifts TypeScript's inferred rootDir and changes the output layout. This is a latent risk for any future sibling config file (e.g. if `apps/web` or `packages/*` ever add one) — check `tsconfig.build.json`'s `rootDir`/`exclude` explicitly whenever a new top-level config file is added to a package that also has its own Dockerfile `CMD` path.
