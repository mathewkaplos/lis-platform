# Implementation Proposal: Upgrade pinned pnpm from 9.15.9 to 11.21.0, restore allowBuilds/injectWorkspacePackages/overrides
Status: APPROVED
ADR: none    Date: 2026-08-15    Backlog ID: issue #267 (lis-platform)

**Approved 2026-08-15** via the native options-prompt (accepted as scoped — pnpm 11.21.0, not the
more conservative 10.26 alternative).

## 1. Goal
Make `pnpm-workspace.yaml`'s `allowBuilds` (supply-chain build-script gating), `injectWorkspacePackages`
(deploy-path package linking), and `overrides` (currently parked in `package.json`'s `pnpm` field)
actually take effect, by upgrading the repo's pinned pnpm from `9.15.9` to a current `11.x`.

**This is a restoration, not new territory** — read directly from `git log`, not assumed:
- TASK-007 (PR #128, 2026-07-26) originally built and verified this repo's Docker/deploy setup
  against **pnpm v11**, adding `injectWorkspacePackages: true` specifically because pnpm v11
  requires it for `pnpm deploy --prod` to produce a self-contained output when the final Docker
  stage only copies the deploy directory (`ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE` otherwise) —
  documented in `engineering/docker-pnpm-monorepo-deploy` Skill entry #2, written at the time.
- PR #266, then PR #269 (2026-08-02), pinned CI and then `packageManager` down to `pnpm@9.15.9` —
  each fixing a real, narrower `--frozen-lockfile`/overrides-mismatch bug (bare `corepack enable`
  drifting to "whatever's newer than v9"), but neither revisited whether v9 itself was the right
  target, versus re-pinning to the v11 already proven working. That reactive downgrade is what
  silently made `allowBuilds`/`injectWorkspacePackages` inert — issue #267 found the symptom
  13 days later, from an unrelated angle (an `overrides` conflict on PR #266 itself).
- This proposal re-establishes one consistent, current pnpm version everywhere (matching PR #269's
  own stated intent — "one canonical version declaration"), this time actually current (11.21.0,
  confirmed via `npm view pnpm@latest` this session) rather than the v9 that was only ever a
  stopgap.

## 2. Affected files
- `package.json` — `"packageManager": "pnpm@9.15.9"` → `"pnpm@11.21.0"`; remove the `"pnpm":
  {"overrides": {"vite": "6.4.3"}}` field entirely (v11 no longer reads `package.json#pnpm` at all —
  confirmed via pnpm's own current docs, Context7 `/pnpm/pnpm.io`).
- `pnpm-workspace.yaml` — add `overrides: { vite: "6.4.3" }` (restoring it to its now-correct
  location, undoing PR #266's workaround). `allowBuilds`/`injectWorkspacePackages`/
  `minimumReleaseAgeExclude` already present, no edit needed to those keys themselves.
- `pnpm-lock.yaml` — fully regenerated by a real `pnpm install` under 11.21.0 (new
  `lockfileVersion`, `settings:`/`overrides:` block, and dependency resolution — pnpm v11 also
  flips `blockExoticSubdeps`/`strictDepBuilds`/`minimumReleaseAge` defaults to stricter values,
  which can change what gets installed, not just how it's recorded).
- `.github/workflows/pr.yml` — no edit expected (already has no explicit `version:` on
  `pnpm/action-setup@v4`, reads `packageManager` — this is exactly the mechanism PR #269 set up).
- `apps/api/Dockerfile`, `apps/gateway/Dockerfile`, `apps/interop/Dockerfile` — no edit expected
  (`corepack enable` + no separate version pin, reads `packageManager` the same way). These three
  are the ones that matter most for this change: each ends in `pnpm --filter <app> deploy --prod
  /prod/<app>` followed by a final stage that *only* copies `/prod/<app>` — precisely the shape
  that needs `injectWorkspacePackages: true` to actually take effect under v11.
- `apps/web/Dockerfile` — unaffected by the deploy-injection concern (uses Next.js's own `output:
  'standalone'` bundling, not `pnpm deploy --prod`), but still goes through the same `pnpm install
  --frozen-lockfile` step and needs to build clean under the new lockfile.
- `~/work/lis-engineering/skills/engineering/docker-pnpm-monorepo-deploy/SKILL.md` — entry #2's
  fix is finally taking effect for real; add a short dated follow-up note (not a rewrite) recording
  that the setting went inert between 2026-08-02 and this fix, and why, so a future session doesn't
  need to re-discover the same regression path.

## 5. Assumptions & autonomous decisions
- Target `11.21.0` specifically (latest published, confirmed via `npm view pnpm@latest` this
  session), not merely "some v11" — pinning to a moving target isn't meaningful, and using the
  actual current release gets the full set of v11 security-default improvements deliberately, not
  by accident of when this proposal happens to be picked up.
- `apps/gateway`/`apps/interop` are not currently deployed to staging (per the current breadcrumb),
  so this proposal verifies their Dockerfiles build correctly under v11 but does not require a real
  staging deploy for them — only `apps/api`/`apps/web` (both currently live on staging) need a real
  `Deploy to Staging` verification.
- `minimumReleaseAgeExclude`'s existing Next.js pin list is assumed to remain valid under v11's new
  enforced `minimumReleaseAge: 1440` default — will be confirmed directly (not assumed) during
  implementation by checking whether the real `pnpm install` under v11 flags any currently-pinned
  package as blocked, and revisited if so.
- No `.npmrc` file exists anywhere in this repo (confirmed this session), so none of v11's
  `.npmrc`-splitting migration concerns apply — nothing to move there.

## 6. Risks
- **New lockfile, real dependency-resolution risk.** pnpm v11's stricter defaults
  (`blockExoticSubdeps: true`, `strictDepBuilds: true`) could newly reject or alter something that
  currently installs cleanly under v9's more permissive defaults. Mitigated by §8's requirement to
  run the full local build/test/typecheck/lint suite against the regenerated lockfile before
  pushing, and by CI itself being the real, authoritative check (per AGENTS.md's "a pass in one
  harness doesn't prove a pass in another").
- **The `pnpm deploy --prod` + `injectWorkspacePackages` interaction is the single highest-risk
  spot** — it's the one thing that's structurally different under v11 versus v9 for this repo's
  own Dockerfiles (not just "a newer version of the same behavior"). If `injectWorkspacePackages`
  doesn't fully resolve it for some reason not anticipated here, the failure mode is a Docker image
  that builds successfully but crashes at container startup (`Cannot find module ...`) — the same
  failure shape `docker-pnpm-monorepo-deploy` Skill entry #9 already documents for a different root
  cause. Mitigated by requiring a real `docker build` + `docker run` (not just a successful build
  exit code) against `apps/api`'s Dockerfile specifically before considering this done, matching
  entry #9's own "validate a Docker/deploy fix with a real local docker build + docker run" rule.
- **This sandbox has no working `docker`** (confirmed this session, `engineering/testing` Skill
  entry #11) — the real Docker build/run verification above cannot happen locally in this session.
  Per that entry's own rule, this proposal relies on CI's `build-and-test` job (which does have
  real Docker available) plus a real `Deploy to Staging` run against `apps/api`/`apps/web`
  specifically, and says so explicitly rather than silently skipping Docker verification.
- **Blast radius:** every workspace package/app reinstalls under a new resolver — this is
  inherently an all-or-nothing change, not something that can be scoped to one app. A revert
  (pin `packageManager` back to `9.15.9`, restore the old lockfile via `git revert`) is
  straightforward if CI or a staging deploy fails.

## 7. Acceptance criteria
- `package.json`'s `packageManager` reads `pnpm@11.21.0`; the `pnpm` field is removed entirely.
- `pnpm-workspace.yaml` carries `overrides: { vite: "6.4.3" }`.
- `pnpm-lock.yaml` is regenerated under 11.21.0 and committed.
- A real `pnpm install` under the new version shows `allowBuilds`/`injectWorkspacePackages` are
  recognized (no longer silently dropped) — verified via the installed pnpm's own `pnpm config
  list`/`pnpm help install` now showing these settings, mirroring how this session confirmed their
  *absence* under v9.
- `apps/api`'s Docker image builds and, once started, serves a real response from its health
  endpoint (verified via CI's `build-and-test` job, since local Docker isn't available this
  session) — proving `injectWorkspacePackages` actually closed the deploy-injection gap for real,
  not just that the build step exited 0.
- Full CI (`pr.yml`'s `build-and-test`, `Constitution Gate`, `storybook-a11y`) green on the PR.
- A real `Deploy to Staging` run (triggered after merge) completes green, and a direct health check
  against the deployed `apps/api`/`apps/web` confirms the running containers actually work — not
  just that the deploy workflow reported success (per `docker-pnpm-monorepo-deploy` Skill's own
  repeated "green step is not proof of real end-state" lesson, entries #9/#10).
- `docker-pnpm-monorepo-deploy` Skill gets the dated follow-up note described in §2.
- Issue #267 closed with a comment summarizing the fix and the "this was a regression from an
  already-working v11 state, not new territory" finding.

## 8. Testing plan
1. `pnpm install` (no `--frozen-lockfile`, regenerating the lockfile for real) under the new
   `packageManager` pin.
2. `pnpm -r typecheck`, `pnpm -r lint`, `pnpm -r test` (unit) — full monorepo, not just one package.
3. `pnpm --filter api test:e2e` if this sandbox's `docker` situation allows it at the time of
   implementation (re-check `which docker && docker ps`, per `engineering/testing` Skill entry #11
   — don't assume it's still unavailable without checking fresh); if not, rely on CI's own e2e run,
   stated explicitly rather than silently skipped.
4. Push to a real PR; confirm CI green via the REST check-runs endpoint (per AGENTS.md's own
   documented `gh` GraphQL-quota-safe polling pattern), not `gh pr checks --watch`.
5. After merge, trigger and verify a real `Deploy to Staging` run — confirm both the workflow's own
   green status *and* a direct, real check against the deployed app (a health-endpoint `curl`/
   `WebFetch` against the actual staging URL, per `docker-pnpm-monorepo-deploy` Skill entry #27,
   or an SSH-based container/log check if available this session) before calling this done.

## 9. Rollback plan
Revert the `package.json`/`pnpm-workspace.yaml`/`pnpm-lock.yaml` commit (pins `packageManager`
back to `9.15.9`, restores the old lockfile and the `package.json#pnpm` overrides workaround). No
migration, no data involved. If the break is caught only after a staging deploy, `rollback-staging.yml`
(referenced in `docker-pnpm-monorepo-deploy` Skill entry #28's context) is the existing mechanism
for reverting the deployed image itself, independent of this revert.
