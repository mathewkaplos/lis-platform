## Notes / gotchas for the next session

- **"Code merged" and "acceptance criterion proven" are different facts.** Confirmed again this session (the drizzle-kit snapshot gap, the two audit_event privilege gaps) — every one of these was found by actually running the migration/check against a real database, not by reading the schema and assuming correctness. Keep applying this skepticism.
- **Hand-written migrations need a manually reconciled drizzle-kit snapshot, or the next `generate` silently corrupts.** New `database-design` Skill entry (lis-engineering) — see TASK-023's finding above. Check this specifically any time a hand-written migration (`0007`/`0008` today) is followed by a `drizzle-kit generate` run.
- **`ALTER DEFAULT PRIVILEGES` only covers what it says it covers — check the actual grant, don't assume it's comprehensive.** Two more instances this session (audit_event's own UPDATE/DELETE, and separately its implicit sequence object) join `postgres`/`BYPASSRLS`, the `meta/*.json` gate false positive, and the `ENABLE ROW LEVEL SECURITY` gate false negative as the same recurring risk class: a table's *real* privileges/policies silently diverging from what its schema/migration "looks like" it grants. Always verify the actual `information_schema.role_table_grants` (or equivalent) state after any new migration that could plausibly interact with `lis_app`'s existing blanket grants, rather than trusting the grant is complete.
- **`rls-isolation-check.ts` (`pnpm --filter @lis/db rls-check`) is now the standing, reusable isolation proof** — extend it (as TASK-025 did, adding an `audit_event` fixture via the real writer) rather than writing a new one-off check per future feature.
